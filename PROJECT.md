# PROJECT.md — паспорт проекта

Файл читается агентом в начале каждой сессии. Это единственный источник
контекста: требования, договорённости, статус и следующий шаг.
В конце каждой сессии агент ОБНОВЛЯЕТ разделы 7 и 8 и включает обновление в коммит.

---

## 1. Суть проекта
3D-игра от первого лица с ASCII-графикой в жанре выживания.
Сеттинг: безлюдная снежная горно-лесная местность (снег, скалы, хвойные
деревья). Проект должен легко расширяться новыми
модулями без переписывания ядра.

## 2. Полные требования (из исходного запроса, не нарушать)

### 2.1 Рендер и визуал
- 3D-сцена от первого лица, отрисованная ASCII-символами.
- Цвет: 32-битный формат клетки (ARGB8888, полные 8 бит на канал,
  ~16.7 млн оттенков). Формат применяется в рендерере напрямую,
  без квантования и отложенных преобразований.
- Разрешение: минимум 1280×720 (720p); рабочие режимы 1600×900 (900p)
  и 1920×1080 (1080p); масштабирование под монитор.
- Полноэкранный режим (или borderless-окно) — реализованный.
- Система освещения: свет влияет на яркость и выбор ASCII-символа.

### 2.2 Игровые системы
- Инвентарь: хранение, выбор, использование предметов.
- Параметры персонажа: здоровье, голод, жажда, холод.
- Крафт: рецепты из доступных предметов (пример: ветка + камень = топор).
- Размещение: установка предметов и построек в 3D-пространстве.
- HUD: отображение статов и служебной информации (FPS и т.п.).

### 2.3 Управление и меню
- Клавиатура: WASD, прыжок, присед, спринт, взаимодействие, инвентарь, крафт, меню.
- Мышь: обзор, захват курсора в игре, освобождение в меню и подобных окнах.
- Переназначение клавиш через меню настроек (динамическое, с сохранением).
- Меню настроек графики: разрешение, полноэкранный режим, яркость,
  дальность прорисовки / плотность символов, ограничитель FPS
  (30 / 45 / 60 / 75 / 90 / 120).
- Меню настроек звука: общая громкость, музыка, эффекты.
- Пауза при открытом меню.

### 2.4 Сохранения
- Сохранение прогресса: позиция, статы, инвентарь, постройки, состояние мира.
- Сохранение настроек и биндов отдельно (config).
- Формат файлов: JSON (System.Text.Json), папка Data.

### 2.5 Архитектура и дистрибуция
- Строгая модульность: Core / Rendering / World / Gameplay / Data / UI.
  Новые модули добавляются без правок ядра.
- Сборка в ОДИН .exe, запускаемый на обычном ПК без установленных средств
  программирования (.NET SDK, IDE и т.п.).
- Целевое железо: Ryzen 5 4600G, RTX 2060 Super, 16 GB RAM — стабильные
  60 FPS вплоть до 1080p включительно; бюджет производительности
  рендерера рассчитывается под 1080p с самого начала.

## 3. Стек и технические решения
- Язык: C# (.NET 8). Обёртка: Raylib-cs (OpenGL-рендер).
- Конфиги и сейвы: System.Text.Json.
- Сборка в один файл:
```
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
```
- Результат: единый exe в bin/Release/net8.0/win-x64/publish.
- CI: .github/workflows/build.yml собирает single-file exe при каждом
  push в main, артефакт AsciSurvival-win-x64; workflow не пересоздавать.

## 5. Технические правила для агента
- Проверенные имена API Raylib-cs и .NET: docs/RAYLIB_API.md, читать
  перед началом работ с рендерингом и вводом.
- Не угадывать имена членов API по памяти: перед первым использованием
  непривычного члена проверить его зондом (мини-программа с reflection
  или тестовая компиляция). Если члена нет в docs/RAYLIB_API.md — провести
  зонд и дописать результат в тот же коммит.
- После смены версии пакета Raylib-cs или TargetFramework файл
  docs/RAYLIB_API.md считается недействительным: регенерировать зондом
  до продолжения работ.
- InputManager использует распарсенный Dictionary<string, KeyboardKey>
  (BindingsMap); не смешивать строковые бинды и энум-бинды в одном поле.
- Полноэкранный режим реализовывать честно (флаг InitWindow /
  ToggleFullscreen), заглушки запрещены.
- Каждый шаг должен компилироваться: выполнять dotnet build в окружении
  и показывать вывод консоли в сессии.
- Не оставлять пустых заглушек в критичных узлах: минимум рабочая
  реализация.
- Комментарии в коде — на русском. Не-русские комментарии запрещены.
- Строковые буферы кадра не должны содержать '\0': только пробел
  для пустых клеток; очистка всех буферов кадра одним ClearFrame().
- Headless-тест рендерера обязан использовать тот же код построения
  кадра, что и игровой рендер (общий метод ядра BuildLine).
- Не перегружать поля структур посторонним смыслом: Brightness хранит
  только яркость, геометрические лимиты — только собственные поля;
  складывание лимитов в семантические поля уже породило баг пола шага 2.6.
- В песочнице запрещён запуск игры с окном (дисплея нет): проверки
  только через dotnet build и dotnet run -- test-frame. Запрещены
  Xvfb, DISPLAY, pkill и аргумент -- headless: его не существует,
  программа уходит в бесконечный игровой цикл.
- Тестовый (test-frame) и боевой пути рендера обязаны вызывать одни
  и те же функции: построение луча (BuildRayThroughCell), композицию
  сцены, построение строки (BuildLine). Расхождение путей уже
  породило баги «чёрный пол» и «рваные формы».
- Data/test_frame.txt содержит ровно один кадр (шапка, 90 строк
  сетки, цветоданные); SaveFrameDump вызывается один раз за прогон.

## 6. Регламент работы сессий

### 6.1 Начало сессии
- Прочитать этот файл (PROJECT.md) целиком.
- Попытаться выполнить git pull origin main. Если remote не определён
  (известный баг платформы: «'origin' does not appear to be a git repository») —
  не останавливаться и не добавлять remote самостоятельно: workspace уже
  содержит актуальный снимок репозитория. Зафиксировать факт в первом ответе.
- Проверить свежесть workspace: если раздел 7 отмечает исправления выполненными, а в коде их следов нет — сообщить и остановиться.

### 6.2 Ветки и коммиты
- Работать ТОЛЬКО в ветке, активной на старте сессии (служебная ветка
  платформы вида qwen-code-...).
- Создавать собственные ветки (feature/..., fix/...) ЗАПРЕЩЕНО: кнопка Publish
  публикует исключительно сессионную ветку.
- Все коммиты делать прямо в сессионной ветке; к концу сессии не оставлять
  незакоммиченных изменений.
- Агент НЕ удаляет ветки и НЕ сливает их в main. Создание pull request в
  штатном режиме выполняет платформа (кнопка Publish) или пользователь
  через сайт GitHub. В аварийном токен-пути (п. 6.4.3) агент может создать
  PR через GitHub API только по прямой команде пользователя.
  Слияние PR в main ВСЕГДА выполняет пользователь.
- Исключение: после аварийного сохранения (п. 6.4.3) слияние спасённой
  ветки в сессионную разрешено ТОЛЬКО по прямой команде пользователя
  в первом сообщении сессии; это единственное разрешённое слияние.

### 6.3 Файлы и коммит-гигиена
- Весь код писать файлами проекта в workspace, а не только текстом в чат.
- Артефакты сборки (bin/, obj/, *.dll, *.pdb) в коммит не попадают
  (контролируется AsciSurvival/.gitignore).
- Перед коммитом обязательна проверка git status: в индексе только исходники,
  csproj, конфиги и PROJECT.md.
- Коммит после каждой подзадачи обязателен до любых рискованных
  операций (запуски с таймаутами, эксперименты с окружением):
  незакоммиченная работа живёт только до смерти контейнера сессии.
- При исчерпании квоты, зависании или Internal Error первое действие
  после восстановления сессии — аварийный коммит и пуш по пункту
  6.4.3, и только затем продолжение работы шага.
- Data/test_frame.txt — генерируемый артефакт: при первой возможности
  снять с отслеживания репозитория (git rm --cached) и внести
  в AsciSurvival/.gitignore.

### 6.4 Публикация (порядок приоритета)
1. ОСНОВНОЙ способ: пользователь нажимает кнопку Publish платформы.
   Обязанность агента до публикации: все изменения закоммичены в сессионную
   ветку, dotnet build проходит с 0 ошибок.
2. Если Publish выдал ошибку («Validation Failed», «No commits between...»,
   «branch update was rejected»): агент проверяет git log сессионной ветки
   (коммиты сессии должны быть её вершиной); пользователь удаляет зависшую
   ветку на GitHub и повторяет Publish.
3. АВАРИЙНЫЙ способ — только после двух неудачных попыток Publish:
   пользователь выдаёт одноразовый токен GitHub (короткий срок, scope repo).
   Агент пушит сессионную ветку на origin и СРАЗУ стирает токен из настроек:
   git remote set-url origin <url без токена>. Токен не записывать в файлы,
   не коммитить, не повторять в ответах. PR создаёт и сливает пользователь
   через сайт GitHub; токен отзывается пользователем сразу после мёрджа.
4. СЕССИОННЫЙ РЕЖИМ (непрерывная работа в одной сессии): пользователь
   выдаёт токен один раз на старте сессии (короткий срок, scope repo).
   Агент настраивает remote с токеном и после каждой принятой
   итерации пушит сессионную ветку БЕЗ отдельной команды, указывая
   хеш коммита в ответе. Токен может оставаться в настройках remote
   до конца сессии; в финальном коммите сессии агент стирает его
   (git remote set-url origin <url без токена>) и указывает это
   в ответе. Создание PR и слияние в main выполняет пользователь
   после внешней сверки кода. Токен не записывается в файлы,
   не коммитится, не повторяется в ответах. Пользователь отзывает
   токен после закрытия сессии. Пункты 6.4.1-6.4.3 продолжают
   действовать для сессий без сессионного режима.
- Агенту ЗАПРЕЩЕНО создавать репозитории, организации, форки и иные
  объекты уровня аккаунта через GitHub API или веб. При 404,
  несовпадении remote или ошибке пуша агент останавливается и
  докладывает улики (git remote -v, полный вывод push). Ожидаемый
  origin: https://github.com/gooseman-ship-it/testrepo69.git.
- Workspace платформы может быть shallow-клоном (признак: grafted
  в git log). Перед пушем ветки в репозиторий, где её ещё нет,
  выполнить git fetch --unshallow origin; ошибка «remote unpack
  missing object» означает нехватку локальной истории, а не
  отсутствие коммита, и лечится unshallow, а не созданием нового
  репозитория.

### 6.5 Конец сессии
- Обновить разделы 7 и 8 этого файла, включить обновление в коммит
   сессионной ветки.
- Финальная проверка: dotnet build — 0 ошибок, 0 предупреждений;
   git status — чисто.
- Одна сессия = один логический шаг из раздела 8 по умолчанию.
  Объединение ДВУХ смежных шагов в одной сессии допускается, если:
  оба шага небольшие и тесно связаны; каждый подшаг завершается отдельным
  коммитом и зелёной сборкой dotnet build; суммарный дифф остаётся
  обозримым (порядка до 10 файлов). Объединение трёх и более шагов
  запрещено. При объединении в разделе 7 помечается статус каждого
  подшага отдельно.
- Приёмка шага по артефактам, а не по нарративу: финальный отчёт
  действителен только вместе с уликами, вставленными в ответ текстом:
  ПОЛНЫЙ дамп headless-теста (все строки сетки, без фрагментов через
  head/tail) — для шагов, затрагивающих рендерер; вывод dotnet build;
  git log --oneline и git status.
- При противоречии отчёта с уликами (дамп, diff, лог сборки, панели
  платформы) приоритет у улик: шаг считается незавершённым и
  доисправляется в той же сессии. Заявка о выполнении критерия
  без улик равносильна невыполнению.
- Сессия не должна завершаться списком «для завершения необходимо»:
  все пункты шага выполняются внутри сессии; завершение с таким
  списком допустимо только при названном объективном блокере
  (например, недоступность инструмента), иначе шаг считается
  незавершённым.
- При изменении состава файлов проекта обновить также раздел 4
  (фактические файлы модулей), включив изменение в тот же коммит.
- Хеш коммита в отчёте обязан существовать на GitHub: пользователь
  или внешний контролёр проверяют, что страница commit/<хеш>
  открывается и ветка присутствует в списке веток. Пометки «пример»,
  «ориентировочно» и синтезированные значения в уликах равносильны
  отсутствию улик и незавершённости шага.
- После публикации и слияния в main сессия закрывается; следующий шаг —
   новая сессия.
