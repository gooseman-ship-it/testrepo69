Ты — агент, выполняющий команды в терминале.
Этот файл читается агентом в начале каждой сессии. Это единственный источник

## 1. Суть проекта
3D-игра от первого лица с ASCII-графикой в жанре выживания.
Сеттинг: безлюдная снежная горно-лесная местность (снег, скалы, хвойные
деревья). Проект должен легко расширяться новыми модулями без переписывания ядра.

## 2. Полные требования (из исходного запроса, не нарушать)

### 2.1 Рендер и визуал
- 3D-сцена от первого лица, отрисованная ASCII-символами.
- Цвет: 32-битный формат клетки (ARGB8888, полные 8 бит на канал,
  ~16.7 млн оттенков). Формат применяется в рендерере напрямую,
  без квантования и отложенных преобразований.
- Разрешение: рабочие режимы 1600×900 (900p)
  и 1920×1080 (1080p); масштабирование под монитор.
- Полноэкранный режим (или borderless-окно) — реализованный.
- Система освещения: свет влияет на яркость и выбор ASCII-символа.

### 2.2 Игровые системы
- Инвентарь: хранение, выбор, всплывающее окно с информацией при наведении на предмет, использование предметов.
- Параметры персонажа: здоровье, голод, жажда, холод.
- Крафт: рецепты из доступных предметов (пример: ветка + камень = топор).
- Размещение: установка (или выбрасывание из инвентаря) предметов и построек в 3D-пространстве.
- HUD: отображение статов и служебной информации (FPS и т.п.).

### 2.3 Управление и меню
- Клавиатура: WASD, прыжок, присед, спринт, взаимодействие, инвентарь, крафт, меню.
- Мышь: обзор, захват курсора в игре, освобождение в меню и подобных окнах.
- Переназначение клавиш через меню настроек (динамическое, с сохранением).
- Меню настроек графики: разрешение, полноэкранный режим, яркость,
  дальность прорисовки / плотность символов, ограничитель FPS
  (30 / 45 / 60 / 75 / 90 / 120).
- Меню настроек звука: общая громкость, музыка, эффекты, громкость персонажа игрока.
- Пауза при открытом меню.
- **Фокус-гейт ввода:** чтение дельты мыши и клавиш движения только при
  активном фокусе окна (`Raylib.IsWindowFocused()`) и захваченном курсоре
  (`IsCursorHidden()`). При потере фокуса кадр замирает без оверлея паузы.
  Дельты мыши с модулем выше 150 пикселей отбрасываются как скачки захвата.
  При возврате фокуса накопленная дельта сбрасывается в ноль.

### 2.4 Сохранения
- Сохранение прогресса: позиция, статы, инвентарь, постройки, состояние мира.
- Сохранение настроек и биндов отдельно (config).
- Формат файлов: JSON (System.Text.Json), папка Data.

### 2.5 Архитектура и дистрибуция
- Строгая модульность: Core / Rendering / World / Gameplay / Data / UI.
  Новые модули добавляются без правок ядра (без прямого указания).
- Сборка в ОДИН .exe файл, запускаемый на обычном ПК без установленных средств
  программирования (.NET SDK, IDE и т.п.).
- Целевое железо: Ryzen 5 4600G, RTX 2060 Super, 16 GB RAM — стабильные
  60 FPS на 1080p включительно; бюджет производительности
  рендерера рассчитывается под 1080p с самого начала.

## 3. Стек и технические решения
- Язык: C# (.NET 8). Обёртка: Raylib-cs (OpenGL-рендер).
- Конфиги и сейвы: System.Text.Json.
- Сборка в один файл: dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
- Результат: единый exe в bin/Release/net8.0/win-x64/publish.
- CI: .github/workflows/build.yml собирает single-file exe при каждом
  push в main, артефакт AsciSurvival-win-x64; workflow не пересоздавать.

## 5. Правила для агента

### 5.1 Общие технические правила
- Проверенные имена API Raylib-cs и .NET: docs/RAYLIB_API.md, читать
  перед началом работ с рендерингом и вводом.
- Не угадывать имена членов API по памяти: перед первым использованием
  непривычного члена проверить его зондом (мини-программа с reflection
  или тестовая компиляция). Если члена нет в docs/RAYLIB_API.md — провести
  зонд и дописать результат в тот же коммит.
- После смены версии пакета Raylib-cs или TargetFramework файл
  docs/RAYLIB_API.md считается недействительным: регенерировать зондом
  до продолжения работ.
- InputManager использует распарсенный Dictionary<string, KeyboardKey>
  (BindingsMap); не смешивать строковые бинды и энум-бинды в одном поле.
- Полноэкранный режим реализовывать честно (флаг InitWindow /
  ToggleFullscreen), заглушки запрещены.
- Каждый шаг должен компилироваться: выполнять dotnet build в окружении
  и показывать вывод консоли в сессии.
- Не оставлять пустых заглушек в критичных узлах: минимум рабочая реализация.
- Комментарии в коде — на русском. Не-русские комментарии запрещены.
- Строковые буферы кадра не должны содержать '\0': только пробел
  для пустых клеток; очистка всех буферов кадра одним ClearFrame().
- Не перегружать поля структур посторонним смыслом: Brightness хранит
  только яркость, геометрические лимиты — только собственные поля;
  складывание лимитов в семантические поля уже породило баг пола шага 2.6.

### 5.2 Правила рендеринга
- Тестовый (test-frame) и боевой пути рендера обязаны вызывать одни
  и те же функции: построение луча (BuildRayThroughCell), композицию
  сцены, построение строки (BuildLine). Расхождение путей уже
  породило баги «чёрный пол» и «рваные формы».
- **Отрисовка в DrawAsciiGrid — посимвольная**, через `Raylib.DrawTextCodepoint`
  с явной позицией клетки `(x * cellWidth, y * cellHeight)`. Run-length
  batching через `DrawTextEx` запрещён, пока не подключён гарантированно
  моноширинный TTF-шрифт. Смешение немоноширинного шрифта и batching
  уже породило баг «клин промахов и кольца» шага 2.7.
- Базис рендера (right/up в BuildRayThroughCell) обязан совпадать
  с базисом движения Camera3D: стрейф вправо и правый край экрана —
  один и тот же вектор. Зеркальный базис равносилен багу управления.
- **HUD-строка координат камеры** `cam=(x,y,z) yaw=.. pitch=..` — служебная,
  не удалять. Используется для сопоставления пользовательских скриншотов
  с headless-дампом.
- **Фокус-гейт ввода:** Camera3D.Update читает дельту мыши и клавиши
  движения только при Raylib.IsWindowFocused() и IsCursorHidden();
  дельты с модулем > 150 пикселей отбрасываются; при потере фокуса
  кадр замирает без оверлея; при возврате фокуса накопленная дельта
  сбрасывается.

### 5.3 Ограничения песочницы
- В песочнице запрещён запуск игры с окном (дисплея нет): проверки
  только через `dotnet build` и `dotnet run -- test-frame`. Запрещены
  Xvfb, DISPLAY, pkill и аргумент `--headless`: его не существует,
  программа уходит в бесконечный игровой цикл.
- `Data/test_frame.txt` содержит ровно один кадр (шапка, 90 строк
  сетки, цветоданные); SaveFrameDump вызывается один раз за прогон.

### 5.4 Схема отчётов debug-report (отложено, вернуться на шаге 2.8)
- На момент 2.7 диагностические секции из Program.cs удалены;
  debug_report.txt содержит только BUILD, RAMP, KEYFILES_SHA256, GIT.
- При переходе к 2.8 (сетка 320×180) схема отчёта расширяется:
  алфавит GRID_W строго {P, B, S, N}; GRID_I содержит индекс
  примитива-победителя (0..N-1) или '.' для промаха; каждая строка
  сетки — ровно 160 или 320 символов; строки COUNTS после каждой сетки.
- Отчёт передаётся дословной вставкой содержимого Data/debug_report.txt;
  передача через diff/patch-обёртки запрещена (обёртки съедают пробелы
  и порождают ложные тревоги).

- Весь код писать файлами проекта в workspace, а не только текстом в чат.

- `Data/test_frame.txt` и `Data/debug_report.txt` — генерируемые артефакты,

### 6.4 Публикация
Приоритет способов публикации:
1. **ОСНОВНОЙ:** пользователь нажимает кнопку Publish платформы. Перед
   нажатием агент обязан убедиться, что: все изменения закоммичены
   (`git status --porcelain` — чисто), `dotnet build -c Release` проходит
   с 0 ошибок, в сессионной ветке есть хотя бы один коммит
   (`git log --oneline -3` показывает свежий коммит с осмысленным сообщением).
2. **Кнопка Publish неактивна или создала пустую ветку.** Типовая причина —
   агент сделал `git add`, но не сделал `git commit`, либо закоммитил не туда.
   Диагностика: `git status --porcelain` (должно быть пусто или только правки),
   `git log --oneline -3` (должен быть свежий коммит). Если коммита нет —
   `git add` + `git commit` + `git push -u origin HEAD`, пользователь затем
   открывает PR вручную через GitHub (Compare & pull request).
3. **АВАРИЙНЫЙ (после двух неудач Publish):** пользователь выдаёт одноразовый
   токен GitHub (scope repo). Агент пушит сессионную ветку и СРАЗУ стирает
   токен из remote. Токен не записывается в файлы, не коммитится,
   не повторяется.
4. **СЕССИОННЫЙ РЕЖИМ (применялся):** токен выдаётся на старте сессии,
   остаётся в remote до финального коммита, где стирается. Пуш после
   каждой принятой итерации без отдельной команды.
- **ЗАПРЕТЫ:** создание репозиториев, организаций, форков через API.
  При 404 или ошибке пуша — остановиться и доложить улики
  (`git remote -v`, вывод push).
- **Shallow-клон:** при grafted в `git log` выполнить
  `git fetch --unshallow origin` перед пушем новой ветки.

- **Запрет предсказанных улик:** любой diff, хеш, вывод команды в ответе —

- **Утверждения о коде:** «уже применено/уже есть» допустимо только после
  чтения региона файла и вставки прочитанного кода в ответ.
- **Исповедь:** в конце ответа перечислить, какие фрагменты — выводы
  инструментов, какие — модельный текст. Модельный текст в полях улик =
  фабрикация.
- **Хеш коммита** обязан существовать на GitHub (страница `commit/<хеш>`
  открывается). Пометки «пример» = отсутствие улик.
- Сессия не должна завершаться списком «для завершения необходимо»
  (кроме объективных блокеров).
- После публикации и слияния в main сессия закрывается, если не было
  сказано иное.
